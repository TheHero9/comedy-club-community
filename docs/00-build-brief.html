Build Brief · Handoff Spec

Podcast Community Platform

A searchable community hub for a group of Bulgarian YouTube podcast channels. This document is the single source of truth for building it — feature scope, tech stack, data model, and phased build plan.

1. Overview & Goals

A web platform (mobile app likely later) where a podcast community can browse every episode across ~5 YouTube channels, rate them, track what they've watched, label what happened in each episode, and search across all of it far more effectively than YouTube's own search. Expected audience: ~1,000+ users.

Transcription is explicitly out of scope for v1. Searchability is achieved for now through community-contributed topic labels and timestamps. A transcription layer can attach to the Episode model later without reworking anything.

Scale reality: This is a small-data, low-traffic app by technical standards (~1k episodes, thousands of users). The architecture below is chosen for clean separation, a future mobile app, and strong AI-assisted development — not because raw scale demands it. Do not over-engineer (no microservices, no Kubernetes needed, no NoSQL).

2. Tech Stack (locked)

Frontend

Next.js (App Router) TypeScript Tailwind CSS shadcn/ui

Server components for SEO (content site — discoverability matters). Highest-quality stack for AI code generation.

Backend

Django Django-Ninja (API) Django Admin

API-first so web + future mobile share one backend. Django admin provides the entire moderation backend (verification, personas, reports) for free.

Data & Search

PostgreSQL Redis Meilisearch

Postgres = source of truth. Redis = cache + Celery broker. Meilisearch = fast, typo-tolerant, Bulgarian-friendly search.

Jobs, Media & Infra

Celery + Celery Beat Cloudflare R2 Docker Fly.io / Railway Cloudflare CDN Sentry PostHog

Background sync + indexing via Celery. R2 for mirrored thumbnails & verification screenshots. Cloudflare in front for CDN/cache/DDoS.

3. Key Decisions & Defaults

Two decisions are annoying to change later. Recommended defaults below — override only with reason:

Auth → managed provider (Clerk recommended). Across API + web + future mobile, hand-rolled JWT is the classic place these apps get insecure. Clerk has the best DX and is AI-friendly; Supabase Auth is a fine alternative. Django maps the external user to a local UserProfile.
Repo → monorepo (Turborepo). Web + API + shared TypeScript types in one repo keeps types in sync across web and mobile and lets AI tooling see the whole system at once.

4. Full Feature Set

Content ingestion

  • Sync multiple YouTube channels (~5 podcasts).
  • Per episode: title, thumbnail, upload date, duration, description, view/like counts.
  • Auto-extract chapters when the creator added timestamps in the description.
  • Daily background sync — new episodes appear automatically.

Users & profiles

  • Sign up / log in; profile with avatar, display name, bio.
  • Channel memberships: which channels a user belongs to, since when, and tier — supports membership in multiple channels.
  • Membership verification by screenshot, reviewed by an admin.

Ratings & scoring

  • Rate any episode 1–10.
  • Two derived scores per episode: Public score (all users) and Elite score (verified members of that episode's channel only).
  • Leaderboards: top-rated, top elite, most-watched, most-commented. (secondary phase)

Personal tracking

  • Mark episodes watched, logged with a date — full rewatch history + "last watched" so users don't accidentally rewatch.
  • Favorite episodes.
  • Private personal tags/keywords for a user's own searching (never public).

Community content

  • Public comments on episodes (describe what happened, discuss). Spoiler flag supported.
  • Community topic labels — reusable canonical topics added by admins or members, enabling "find every episode about X".
  • Community timestamps / "moments" (e.g. "funny bit at 34:12").
  • Up/down voting on topic labels so good ones surface.

People / personas

  • Admin-managed personas (hosts, co-hosts, guests), optionally linked to a real user account.
  • Attach participants to each episode with a role.
  • Browse every episode a given person appeared in.

Search

  • Search across episodes by title, topic, community labels, and moments.
  • Meilisearch for fast, typo-tolerant, Bulgarian-friendly results (Postgres full-text is an acceptable v1 fallback).

Moderation

  • Generic report queue — flag bad labels, comments, or timestamps; states: pending / resolved / dismissed.
  • Admin & moderator roles; Django admin handles verification, personas, and reports.

Elite score is derived, not a separate vote. One Rating model; the elite score = average of ratings from users who are verified members of that episode's channel. When a user gets verified, their existing rating automatically starts counting toward elite.

6. Ingestion (YouTube → DB)

Thumbnails need no API — they're at a deterministic URL from the video ID:

https://img.youtube.com/vi/{VIDEO_ID}/maxresdefault.jpg   # best, not always present
https://img.youtube.com/vi/{VIDEO_ID}/hqdefault.jpg       # always exists (fallback)

Strategy: try maxresdefault, fall back to hqdefault. Store the video ID; build the URL. Optionally mirror images to R2.

Metadata: use yt-dlp for the bulk backfill of all ~1,000 videos (no API key, richest data), and the official YouTube Data API v3 for ongoing daily syncs (stable, TOS-blessed, free quota ~10k units/day). Example backfill call:

yt-dlp --dump-json --skip-download "https://www.youtube.com/watch?v={VIDEO_ID}"

Fields to capture: id, title, description, upload_date, duration, thumbnails, view_count, like_count, chapters. After each sync, push new/updated episodes into the Meilisearch index (Celery task).

7. Build Plan (phased)

0Scaffolding. Monorepo (Turborepo). Django + Django-Ninja backend, Next.js frontend, Postgres/Redis/Meilisearch via Docker Compose. Wire Clerk auth end-to-end. Sentry + PostHog stubs.
1Ingestion. Channel + Episode models, yt-dlp backfill command, thumbnail handling, daily Celery Beat sync. Goal: episodes flowing into the DB and visible in Django admin.
2Browse + profiles. Public episode/channel browsing on the frontend, user profiles, ratings, watch log, favorites.
3Membership + scoring. Channel memberships, screenshot verification (admin), derived public + elite scores.
4Community + search. Comments, canonical topics/labels, personal tags, community moments, Meilisearch-powered search.
5People + moderation + leaderboards. Personas & participants, report queue, leaderboards and user lists.
6Later (optional). Transcription layer; mobile app (React Native/Expo, reuses the API).

8. Constraints & Notes

  • No transcription in v1 — searchability comes from community labels + moments for now.
  • Don't over-engineer — no microservices, Kubernetes, or NoSQL. Cache reads (Cloudflare + Redis) and denormalize aggregate scores onto Episode with periodic recompute before reaching for anything fancier.
  • SEO matters — this is a content site; use Next.js server rendering so episodes are discoverable via search engines.
  • Language — content and much of the UI is Bulgarian; ensure search tokenization and any UI copy handle it. Meilisearch handles Bulgarian well.
  • yt-dlp vs Data API — yt-dlp is scraping and can break on YouTube changes; the Data API is stable but quota-limited. Use yt-dlp for bulk backfill, Data API for ongoing sync.
  • Companion file: the full Django models.py is the canonical schema; generate migrations from it.

Instruction to the building assistant: implement phase by phase, confirming each phase runs before moving on. Prefer boring, well-supported solutions. Keep shared types in the monorepo so web and future mobile stay in sync. Ask before making schema changes that deviate from the companion models.py.
