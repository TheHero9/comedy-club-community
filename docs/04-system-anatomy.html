A community platform for Bulgarian YouTube comedy podcasts. Members browse every episode across every channel, rate them 1-10, log what they watched, and label what happened and when. The whole product is one search box and a grid of scores. Everything below is what it takes to make those two things correct.

Layer 1 · The shape

Six moving pieces, one hard rule

The website never talks to a database. Not once. Every single read and every single write goes through the Django API. That one restriction is why a phone app can be added later without rewriting anything on the server.

Layer 2 · The data

19 tables, and the two they all point at

The schema is a sandwich. YouTube content sits on top. Real people sit at the bottom. Everything the community produces lives in the middle, because every one of those tables is literally a join between an episode and a user. Two tables carry the whole graph: Episode has 10 tables pointing at it, User has 15 columns pointing at it.

Layer 3 · The rule that runs the product

One rating. Two numbers.

This is the piece most likely to be built wrong, so it is built once and defended by tests. There is a single Rating table. Everything else is derived from it.

Public score

The average of every rating on the episode. Anyone signed in can move it.

Elite score

The average of ratings left by people with a verified paid membership of that specific channel. Not a separate vote, not a second table - the same rows, filtered.

Why that matters

The moment a moderator ticks "verified", every rating that person has ever left starts counting toward elite. No backfill. No duplicated rows. No migration. The design choice is the feature.

The seven bands, and the eighth thing that is not a band

Scores render as coloured chips. All seven sit in a narrow lightness range so they read as one family and every one of them can carry the same near-black text. They are declared once and are identical in light and dark, because a colour that changes with the theme would look like a value that changed.

Masterpiece Awesome Great Good Regular Bad Garbage ?  Unrated

That last chip is 22% of the catalogue. An unrated episode is not a zero and not the bottom band - it renders as a question mark on a dashed outline, because scoring an episode nobody has watched as "garbage" would be a lie the colour tells before anyone reads the number.

Layer 5 · The work nobody sees

Everything that runs while nobody is looking

Jobs are thin wrappers over the same service functions the typed commands call, so a scheduled run and a manual run can never diverge into two behaviours.

14 background jobs

  • sync_channel / sync_all_channels - pull new episodes
  • recompute_episode_score - fires on every rating write
  • recompute_all_scores - the self-healing sweep
  • recompute_membership_scores - runs when a verification flips
  • reindex_episode / reindex_channel / rebuild_search_index
  • remove_episode_from_index - deletions have to propagate too
  • fetch_episode_transcript / backfill_transcripts
  • reindex_transcript / rebuild_transcript_index / remove_transcript_from_index

3 schedules

  • 04:00 daily - sync every active channel for new episodes
  • :20 hourly - score sweep. Ratings already recompute on write, so this only repairs drift from a lost signal or a verification change
  • 05:00 nightly - full search rebuild, so a dropped indexing task cannot leave the index quietly wrong overnight

7 operator commands

  • backfill_channel - the one-time bulk import
  • repair_metadata - re-fetch rows a throttle degraded
  • refresh_channel_meta - avatars move when an owner changes their picture
  • backfill_transcripts - free captions where they exist
  • reindex - rebuild both search indexes from Postgres
  • seed_demo - fake community data on real episodes, with an exact inverse
  • sync_channels - the daily path, runnable by hand
Layer 6 · The actual product

Two indexes, because they answer two questions

The entire reason this platform exists is that YouTube's search across these channels is bad. So search is the one place where being clever was mandatory.

episodes

"Which episodes are about this?"

Title, description, channel name, community topic labels, moment labels and participant names, all in one document. Falls back to Postgres full-text search behind the identical endpoint if Meilisearch is unavailable, so search degrades instead of disappearing.

transcript_segments

"Where was this said?"

A separate index, and the separation is load-bearing. Putting a 26,000-word transcript next to a 60-character title in one document makes every episode match nearly every common Bulgarian word, and a passing mention outranks an episode genuinely about the subject. Results carry a second-accurate deep link into the video.

The honest caveat, shipped in the UI

Transcript coverage is partial and depends on the upload date. Sampled 2024-2026: 9 of 9 episodes had Bulgarian captions. Sampled 2019-2022: 0 of 12. Members-only: 0 of 5. So transcript search is never presented as exhaustive - an episode that does not appear has not been ruled out, it may simply have no captions. Saying that out loud in the interface was cheaper than pretending otherwise and being wrong.

The part that took the time

Nine bugs that all looked like something else

Writing the features was the fast half. Every item below shipped green: it passed the type checker, passed the linter, passed the build, and was still wrong. This is what the difficulty actually consists of.

A 1,318-episode import reported "0 errors" and was quietly a quarter wrong

What it looked like
A perfect backfill. Every episode created, no exceptions raised, titles and dates all present.
What it actually was
YouTube had soft-blocked the run partway through and started serving a reduced payload. The scraper does not error on this. Silently missing: duration, view_count, like_count and availability on 1,036 of 1,318 rows.
The dangerous half
A missing availability was coerced to "public". So a paywalled members-only episode was stored as confidently public. A missing duration is visibly wrong; a wrong paywall flag looks exactly like a right one.

Fix: never judge an import by its error count. duration_sec IS NULL is the marker of a degraded row, because a complete response always carries a duration. The block lasts hours, not minutes - probing 8 videos immediately after recovered 0 of 8.

Then the repair for that bug was recorded as done without being checked

What it looked like
The repair command had been run. The status document said "metadata complete."
What it actually was
The repair had been started while the block was still active. It correctly refused to write anything from an incomplete response - which is the right behaviour - and 1,076 rows were still broken. The claim was written down anyway.
How it surfaced
Nothing in the app complained. It came out sideways: the demo seeder produced a quarter of the expected moments, because a moment needs a duration to pick a timestamp inside.

Fix: a run finishes with the COUNT, never with the command. The re-run recovered all 1,076 rows with zero availability corrections, so nothing had been mis-flagged - the loss was duration and view count only.

Typo tolerance is measured in bytes, and Cyrillic is two bytes a letter

What it looked like
Catastrophically broken search relevance. The Bulgarian query for "pizza" returned 100 results, of which 95 were wrong - it was matching a completely unrelated word that differs by one letter.
What it actually was
The minimum word length for typo tolerance was configured as {4, 8}, believing those were characters. The engine measures bytes. In Cyrillic that is 2 and 4 characters, so nearly every Bulgarian word qualified for fuzzy matching.
How it was proven
A sweep across every threshold value. False matches persisted up to 8 and stopped dead at 9 - exactly the byte length of the four-letter query.

Fix: thresholds are now written as an explicit multiplication by bytes-per-Cyrillic-character, so the unit is impossible to forget.

Every descending index in the database was dead

What it looked like
Correctly declared indexes on every sort column. Lists were slow anyway.
What it actually was
A plain descending index compiles to NULLS FIRST. But every list sorts NULLS LAST, because an unrated episode must never top "top rated". Postgres cannot use one ordering for the other, so the indexes had idx_scan = 0 and every list page was a full table scan plus a sort.

Fix: expression indexes matching the actual ORDER BY, tiebreak column included. Measured on the real table: cost 1624 → 24, execution 23ms → 0.3ms.

One file turned every 404 on the site into a blank page that said 200

What it looked like
A loading skeleton. Good practice. Ordinary.
What it actually was
A loading file at the app root wraps every page in a suspense boundary, so the framework flushes the HTML shell with a 200 before the page resolves. Every "not found" on the site silently became a soft 404: status 200, empty body. The pages had been calling not-found correctly the entire time.
Why it mattered here
The whole point of this site is being indexable. Google would have crawled every dead episode link as a real page.

Fix: skeletons are scoped only to routes that cannot 404, and a test now curls a deliberately bad URL and asserts the status code, not that "the page looks right".

An API returning 500 showed up in the browser as slightly outdated numbers

What it looked like
A flaky test. The ratings grid disagreed with the API by a little. Logged as an unexplained flake and set aside for a session.
What it actually was
Two bugs stacked. The dev server holds one database connection per request thread with no bound, so a 600-second connection lifetime exhausted Postgres: 8 concurrent requests produced 14 failures out of 32, and end-to-end failures accumulated across runs. Meanwhile the frontend serves a stale cache entry when revalidation fails - so a hard 500 surfaced as plausible, slightly wrong data instead of an error.

Fix: connection lifetime pinned to 0 in development by a test that fails if anyone changes it. Result: 48 concurrent requests, 192 of 192 succeeded. Lesson: when a page and its API disagree, check whether the API was erroring - not just whether the numbers moved.

A search for "???" returned the entire catalogue

What it looked like
A total relevance collapse, apparently specific to Cyrillic: a real Bulgarian word returned everything, gibberish returned nothing.
What it actually was
Two layers. First, the terminal was mangling Cyrillic command-line arguments into literal question marks before the request was even sent. Second - and this was a real bug - a query that tokenizes to nothing was reaching the search engine, which read it as a placeholder and matched every document in the index.

Fix: a shared "does this contain anything searchable" check in front of both search endpoints, and Cyrillic is now only ever tested from a UTF-8 source file, never through a shell.

A single invisible character crashed the server, and the fix had to be in one place

What it looked like
A 500 with no obvious cause.
What it actually was
A NUL byte. It is legal in a URL, legal in a JSON string, passes every validation rule the API declares, and then fails deep inside the database driver.
Why the fix location matters
Rejected once in middleware covering path, query string and JSON body recursively - not per endpoint. Same reasoning as the rate limiter: a new endpoint must not be able to ship vulnerable by omission.

Half the fix was on the other side: a 4xx thrown inside a server-rendered page is an unhandled exception and therefore a 500 error page, so control characters are stripped at the edge too - control characters only, since a sanitiser that ate Cyrillic would break every real Bulgarian URL while still passing the NUL test.

The eleventh click of "Load more" served a 500 to an ordinary user

What it looked like
Nothing. Ten clicks worked perfectly. Nobody clicks eleven times while testing.
What it actually was
The frontend capped the page size at 200. The API capped it at 100. Each click grows the request by 9, so the eleventh crossed the API's limit and returned an error.

Fix: a test parses the constant out of the Python source and fails the build if the two numbers drift apart. Also floors the value, because a decimal string is finite and positive and still a validation error against an integer parameter.

Why any of it can be trusted

958 tests, and a rule about never weakening one

Three bugs shipped during the initial build and all three passed the type checker, the linter and the build. Static tools could not see any of them. Each now has a named regression test.

Tests that test the tests

  • Assertions run against the live API response, never a hardcoded score, because ratings change and the real invariant is "the interface matches the API"
  • Every loop is guarded by a fixture check, so a test cannot pass by iterating over nothing
  • Every intercepted network call is proven to have fired with a hit counter, because a server-rendered fetch never crosses the browser and a test that intercepts it passes vacuously
  • The two score-recompute code paths are compared against each other, never against fixed numbers, so tuning one alone breaks the suite
  • A scanner parses every component and fails on any hardcoded user-facing string, so translated copy cannot leak back into the code
  • Accessibility violations fail the build outright

Explicitly banned

  • Skipping a test to dodge a failure
  • A try/catch that swallows an assertion
  • Filler assertions that cannot fail
  • Widening an error allow-list to silence a real console error

If a test fails, the app gets fixed. A test loosened to go green is worse than no test, because it reports safety that does not exist. Where something genuinely cannot be covered, it is left uncovered with a written reason - an honest gap beats a green test that proves nothing.
